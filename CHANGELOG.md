# Changelog
## 1.3.7 — 2026-11-19
- Removed: the "file is N MB. Continue?" prompt when loading a large file into the panel. It interrupted exactly the workflow the extension is for — big exports loading (including automatic loads when following the active editor) — and Amit's instruction was plain: don't bug the users with this. Large files now just load, with progress in the source bar as before. The csvQuery.enableLargeFileWarning / csvQuery.largeFileWarningMB settings are gone with it.
## 1.3.6 — 2026-11-19
- Fix: follow-the-editor ignored files displayed in the Color Editor. Once Color Columns started working on big files, those files sit in Color Editor (custom) tabs — and the follow logic only recognised text editors and text tabs, so switching to a coloured file never loaded it and follow appeared to stop entirely "no matter what tab I am on". A file shown in the Color Editor is now a follow target like any other (pickFollowTarget gained a colorEditor branch, unit-tested); foreign custom editors remain ignored.
## 1.3.5 — 2026-11-19
- Fix (the actual root cause of the black Color Editor in every version since 1.3.0): activation registered the query panel twice — registerCommands and activate() both call QueryPanel.register(), and the second call's duplicate webview-view registration threw, aborting activate() BEFORE the Color Editor provider registration line was ever reached. VS Code therefore opened Color Editor tabs from the package manifest with no provider behind them: no openCustomDocument, no resolve, no error in the extension's own log. QueryPanel.register() is now idempotent, the Color Editor provider registers first, and activation is wrapped so any failure logs "ACTIVATION FAILED: …" to the CSV Query channel, with "Color Editor provider registered." and "Activation complete." lines proving the sequence ran.
## 1.3.4 — 2026-11-19
- Color Columns reshaped to what was actually asked for — "paint the current file itself, query window below". For files VS Code syncs to extensions (up to the ~50 MB sync limit, plus untitled buffers) the open editor is now painted IN PLACE with text decorations: no new tab, no editor change, painting follows scrolling and editing and is remembered per file. For files above the sync limit there is no document any extension can paint, so the toggle instead flips the file's ONE tab between the plain text editor and the Color Editor (the old tab closes as the new one opens, and flips back on the next click). Editor following is debounced (300 ms) so a tab flip doesn't make the panel chase the neighbouring tab mid-swap.
## 1.3.3 — 2026-11-19
- Fix: the Color Editor tab opened black with the log stopping at "Opening Color Editor for …" — VS Code never called resolveCustomEditor. The provider omitted openCustomDocument, which the VS Code API defines as a required step of CustomReadonlyEditorProvider ("openCustomDocument is called when the editor is first opened; the opened document is then passed to resolveCustomEditor"). It is now implemented (the document is just the URI — content streams from disk via the line index), with its own log line so the startup sequence is fully observable.
## 1.3.2 — 2026-11-19
- Fix: the Color Editor could open to a black, silent tab. Its startup was gated entirely on the webview page's 'ready' message — in the failing session the Output log showed the toggle click and then nothing: no resolve, no indexing, no error. Indexing now starts the moment the editor resolves (the data pipeline itself is proven: a 68 MB file indexes in ~120 ms), 'ready' re-sends the editor state in case the first send raced the page load, the first window of lines is served proactively, and every step (open, resolve, html, each webview message, indexing, first serve, and any script error in the page) is logged to the CSV Query output channel so a failure names its step.
## 1.3.1 — 2026-11-19
- Fix: follow-the-editor missed two cases, both proven by the Output log. (1) Files over VS Code's 50 MB sync limit produce no active-editor event a extension can use — the panel now also follows the active TAB (the Tabs API reports large-file tabs and their URIs even when their documents are not synced). (2) The editor restored with the window never fires a change event, so a fresh window's panel sat empty ("No file loaded yet") while a data file was already open, and Run queried a stale or empty table — the panel now syncs to the current editor/tab once when its view first resolves. Target selection is a pure, unit-tested function (document wins when synced; tab is the fallback; the Color Editor and webview tabs are never followed).
## 1.3.0 — 2026-11-18
- The panel now **follows the active editor**: switch to another data file and it loads automatically, so the results always describe the file you are looking at (previously the panel stayed bound to whatever was last opened explicitly). Switching files cancels a load still in progress instead of queueing behind it, rapid switching loads only the file you land on, and the scan pass of a large load now reports progress ("Scanning … N rows scanned") instead of sitting silent. Turn it off with `csvQuery.followActiveEditor`.
- Color Columns is now a proper editor: the **CSV Query Color Editor**, a custom editor that takes over the file's own tab and colours EVERY line — not a separate 300-line preview. A byte-offset line index is built once per file (streamed, cached), and the editor renders a moving window of lines read from disk on demand, so a 3.7M-line file scrolls end to end at constant memory. Open it with the panel's Color Columns button (click again to close), by right-clicking a file → "Open in Color Editor", or via "Open With…". It follows the panel's delimiter when the file is loaded there, and updates live if the delimiter changes. The Color Editor is read-only — reopen the file with the Text Editor to edit it. The 300-line preview remains only for untitled/unsaved buffers, which have no file for the editor to open. Why a custom editor at all: above 50 MB VS Code will not expose a file's document to extensions, so painting the built-in editor is impossible for large files — a custom editor is the one way to have the file itself, in its tab, coloured all the way through.
## 1.2.4 — 2026-11-18
- Fix: loading a very large file failed with "Invalid string length". The loader read the whole file into a single string (and held every parsed row in memory); V8 caps a string at ~512M characters regardless of RAM, so a multi-hundred-MB export could never load. File loads now stream from disk in two passes — pass 1 finds the true column width, counts rows and detects the header; pass 2 inserts in 500-row batches — so peak memory is the SQLite database plus one batch, and there is no string-length ceiling. Semantics are unchanged (quote-aware parsing, blank-line skipping, ragged rows padded to the widest row, header detection). "Add File as Table" streams the same way, and delimiter/header changes on a disk-loaded file re-stream it instead of reusing the preview's head sample.
## 1.2.3 — 2026-11-18
- Color Columns redesigned around a hard platform limit, found via the Output log on a real 91.6 MB file: above 50 MB VS Code refuses to give extensions the document at all ("Files above 50MB cannot be synchronized with extensions"), so painting colours into the editor is impossible for exactly the large files that need them — no extension can do it. Color Columns now opens a colourised preview of the loaded file's first 300 lines, rendered from the text the panel already read from disk, so it works at any file size. The preview refreshes on reload and delimiter changes, the results-grid header tints are unchanged, and the toggle button now reflects whether the preview is open. The editor-decoration implementation (1.2.0–1.2.2, never published) is removed.
## 1.2.2 — 2026-11-18
- Fix: the Color Columns toggle could still dead-end with the "open a delimited file" warning while the file was open and loaded — its fallback consulted only the *active* editor, which is unreliable while focus sits in the panel webview. The toggle now mirrors the source-resolution fallback chain (panel source document, including via a visible editor → active editor → any visible editor) and logs which path it took to the CSV Query output channel.
## 1.2.1 — 2026-11-18
- Fix: the Color Columns toggle dead-ended with "load a file first" when the panel had no source loaded in this session (e.g. right after installing an update) or when a disk-loaded source could not be opened/shown in an editor. The toggle now falls back to the file in the active editor, and a failure to show the source document no longer blocks colouring (the colours paint when the file becomes visible).
## 1.2.0 — 2026-11-18
- New: **Color Columns**. A toggle button next to Export Results (and a "CSV Query: Toggle Column Colors" command) paints each column of the delimited file in the editor a different colour, so the structure of a wide raw file is visible at a glance; the results grid's column headers take the same colours, so a column's colour matches between the file and your results. Painting is quote-aware, uses the panel's delimiter (and follows it when changed), is remembered per file, and only ever paints the lines on screen — so it stays instant on million-row files. New setting `csvQuery.colorColumnsByDefault` (default off) turns it on automatically for every file loaded in the panel. Known limit: a quoted field containing a literal line break can misalign colours on following lines.
## 1.1.1 — 2026-11-18
- Opening Query History now auto-scrolls the panel to the history area, so it is visible immediately instead of opening below the fold where a scroll was needed to notice it.

## 1.1.0 — 2026-11-18
- The query UI now lives in the Panel area below the editor instead of opening as a tab beside the file (requested in user feedback), so the data file keeps the full editor width and the query workspace sits underneath it. Same commands and shortcut — "CSV Query: Open Query Panel" now reveals and focuses the view in the bottom Panel.
- The SQL editor hugs its content: it is exactly one line tall for a one-line query and grows as lines are added (capped at 40% of the view height, then it scrolls internally), instead of a fixed ~6-line block that could not shrink.
- Query history no longer occupies permanent space under the results: it is behind a History toggle button next to Export Results, collapsed by default; click to show, click again to hide. Entries still restore on click.
## 0.1.0 — 2026-11-06

## 0.1.1 — 2026-11-06
- Fix: "open a delimited file first" could fire even with a delimited file open (reported on SHC_General_Ledger_Detail_10302026.txt). Context-menu commands now use the file they were invoked on (Explorer passes a Uri, which v0.1.0 ignored), and Open Query Panel falls back to any visible editor, then to the panel's already-loaded document, then to a file picker instead of a dead-end warning.
- Fix: Reload now reloads the document the panel was loaded from (including unsaved changes) instead of whatever editor is active — focus is normally in the webview when Reload is clicked.
## 0.1.2 — 2026-11-09
- Fix: panel could sit on "Loading…" forever (SJ_Workday_Project file). The source message was posted as soon as the panel was created, before the webview had signalled it was ready to receive messages, and could be lost; the panel then never updated. Extension-to-webview messages are now queued until the webview's ready signal, flushed in order, and the full source/result state is resent on ready.
- Fix: loading is no longer one long synchronous block with feedback only at the end. The panel immediately shows "Loading <file> (<size> MB)…", then live row progress during a chunked, yielding bulk insert (500 rows per INSERT), then the final source line.
- Fix: a load failure now replaces Loading with "Failed to load <file>", shows the error in the panel, and raises a VS Code error notification — never a silent stuck panel.
## 0.1.3 — 2026-11-09
- Fix: panel buttons (Run, Reload, Add File, Export, Format, Clear) did nothing and the panel stayed on "Loading…", even though the script tested clean in isolation — the inline-script/nonce webview is replaced wholesale. The webview script and styles are now real files (media/main.js, media/styles.css) loaded via asWebviewUri under a cspSource CSP, with no inline script or nonce at all; buttons are wired with addEventListener, and the script hides a "script has not run" banner and posts ready as its very first actions.
- Diagnostics: the extension now logs to an Output channel ("CSV Query" in View → Output) — activation, document resolution, load counts/timing, every webview message received, and any webview client error (relayed by the script's window.onerror handler).
- Regression test: test/webview.test.ts executes the exact shipped media/main.js in a stub DOM and asserts ready is posted, Run posts the SQL, Clear empties the editor, and a source message updates the bar.
## 0.1.4 — 2026-11-09
- Fix: files above 50 MB failed with VS Code's "Files above 50MB cannot be synchronized with extensions" (hit on SHC_General_Ledger_Detail_10302026.txt). File-backed sources are now read directly from disk with fs.readFile and never go through TextDocument.getText()/openTextDocument: Explorer context-menu targets are not opened as documents at all, and clean editor files are read from disk too. The editor buffer is only used for untitled documents and unsaved changes to files under the 50 MB limit; a dirty file over the limit queries the saved version and says so in a warning.
- Verified: unit tests for the read-strategy decision, and an end-to-end run on a synthetic 55.8 MB pipe-delimited file (disk read → parse → SQLite load → query) in the test VM.
## 0.1.5 — 2026-11-09
- Fix: "Maximum call stack size exceeded" loading the SHC ledger. The parser computed column width with Math.max(...rows), which spreads every row as a function argument — reproduced locally: it throws RangeError at 200,000 rows (and survives 100,000 in Node; the extension host's limit is in that range). Width is now computed with a plain loop, and an audit confirmed no other row-count-scaling call spread or apply() exists in the load path.
- Regression test: parsing 300,001 rows succeeds. End-to-end in the test VM: a 210,000-row pipe-delimited file reads from disk, parses in ~0.4s, loads into SQLite in ~1.8s, and queries correctly.
## 0.1.6 — 2026-11-09
- No more result limits (the ledger's query returned 1,692,797 rows, but only 100,000 could be exported and only the first 10,000 browsed). The 100k maxResultLimit cap is removed: Export now streams the complete result set of the last query to the file, one statement step at a time, with no row cap and without holding the whole result in memory.
- The grid now pages through the entire result set: queries run as a counted subquery, 1,000 rows per page, and Prev/Next fetch further pages from SQLite — all 1,692,797 rows are reachable. A LIMIT you write in your own SQL is still respected, because it bounds the subquery. csvQuery.defaultResultLimit / maxResultLimit are deprecated and no longer restrict anything.

## 0.1.8 — 2026-11-09
- Documentation only (prompted by r/vscode feedback): new README section "Working with numbers" — filter IDs as text, use CAST for numeric comparisons/sorting/totals, plus the two verified gotchas (CAST of empty/non-numeric is 0; strip $ and thousands separators with REPLACE before casting, e.g. $1,234.56 → 1234.56). No code changes from 0.1.7.
## 0.1.9 — 2026-11-10
- Column names: spaces are removed from header names when a file is loaded, so "Spend Category" is queried as SpendCategory and "Revenue Category" as RevenueCategory, with no quoting needed (requested after a real ledger query failed on the spaced name). Original header text is kept as the display label; if two headers collide after stripping (e.g. "Spend Category" and "SpendCategory"), the later one is suffixed _2. Note: saved queries/history that quoted the old spaced names ("Spend Category") need the new name. 32/32 tests, including an end-to-end run of the exact ledger query.
## 0.1.10 — 2026-11-10
- Export is now a proper download flow: the save dialog is pre-filled with "<source>_results.csv" in the source file's own folder (workspace folder or home for untitled sources), so clicking Export Results and confirming saves the CSV right next to the data instead of an un-named file in an arbitrary folder. After the write, the confirmation names the file and offers "Reveal in Finder" / "Open File". Streaming of the complete result set with no row cap is unchanged.
## 1.0.0 — 2026-11-10
- First stable release. CSV Query for VS Code graduates from the 0.1.x series: SQLite SQL on any delimited file (table THIS, all columns TEXT, leading zeros preserved), files read directly from disk with no size-driven sync limit and no result caps (grid pages the complete result set 1,000 rows/page; export streams it in full), space-stripped column names, the export download flow (pre-filled "<source>_results.csv" in the source folder), query history, multi-file joins, and the "Working with numbers" CAST guidance. Battle-tested on a real 1,692,797-row general-ledger export and shaped by user reports from the Marketplace and Reddit. Source now maintained on GitHub.
