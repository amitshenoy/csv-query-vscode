# Changelog
## 0.1.0 — 2026-11-06
- Phase 1 MVP + Phase 2 polish + core Phase 3: open query panel on any/unsaved file, delimiter & header detection, in-memory sql.js SQLite with THIS table, all-TEXT columns, Cmd/Ctrl+Enter, friendly errors, sortable/filterable paginated grid, persistent query history, CSV/TSV export, reload, settings, context menus, multi-file tables and joins, large-file warning.
- Known limits: grid pagination is 500/page instead of true virtualization; SQL highlighting in the editor is plain monospace (no syntax colours); streaming chunk-parse for >200 MB files is warned, not yet chunked.
## 0.1.1 — 2026-11-06
- Fix: "open a delimited file first" could fire even with a delimited file open (reported on SHC_General_Ledger_Detail_10302026.txt). Context-menu commands now use the file they were invoked on (Explorer passes a Uri, which v0.1.0 ignored), and Open Query Panel falls back to any visible editor, then to the panel's already-loaded document, then to a file picker instead of a dead-end warning.
- Fix: Reload now reloads the document the panel was loaded from (including unsaved changes) instead of whatever editor is active — focus is normally in the webview when Reload is clicked.
## 0.1.2 — 2026-11-09
- Fix: panel could sit on "Loading…" forever (SJ_Workday_Project file). The source message was posted as soon as the panel was created, before the webview had signalled it was ready to receive messages, and could be lost; the panel then never updated. Extension-to-webview messages are now queued until the webview's ready signal, flushed in order, and the full source/result state is resent on ready.
- Fix: loading is no longer one long synchronous block with feedback only at the end. The panel immediately shows "Loading <file> (<size> MB)…", then live row progress during a chunked, yielding bulk insert (500 rows per INSERT), then the final source line.
- Fix: a load failure now replaces Loading with "Failed to load <file>", shows the error in the panel, and raises a VS Code error notification — never a silent stuck panel.
## 0.1.3 — 2026-11-09
- Fix: panel buttons (Run, Reload, Add File, Export, Format, Clear) did nothing and the panel stayed on "Loading…", even though the script tested clean in isolation — the inline-script/nonce webview is replaced wholesale. The webview script and styles are now real files (media/main.js, media/styles.css) loaded via asWebviewUri under a cspSource CSP, with no inline script or nonce at all; buttons are wired with addEventListener, and the script hides a "script has not run" banner and posts ready as its very first actions.
- Diagnostics: the extension now logs to an Output channel ("CSV Query" in View → Output) — activation, document resolution, load counts/timing, every webview message received, and any webview client error (relayed by the script's window.onerror handler).
- Regression test: test/webview.test.ts executes the exact shipped media/main.js in a stub DOM and asserts ready is posted, Run posts the SQL, Clear empties the editor, and a source message updates the bar.
## 0.1.4 — 2026-11-09
- Fix: files above 50 MB failed with VS Code's "Files above 50MB cannot be synchronized with extensions" (hit on SHC_General_Ledger_Detail_10302026.txt). File-backed sources are now read directly from disk with fs.readFile and never go through TextDocument.getText()/openTextDocument: Explorer context-menu targets are not opened as documents at all, and clean editor files are read from disk too. The editor buffer is only used for untitled documents and unsaved changes to files under the 50 MB limit; a dirty file over the limit queries the saved version and says so in a warning.
- Verified: unit tests for the read-strategy decision, and an end-to-end run on a synthetic 55.8 MB pipe-delimited file (disk read → parse → SQLite load → query) in the test VM.
## 0.1.5 — 2026-11-09
- Fix: "Maximum call stack size exceeded" loading the SHC ledger. The parser computed column width with Math.max(...rows), which spreads every row as a function argument — reproduced locally: it throws RangeError at 200,000 rows (and survives 100,000 in Node; the extension host's limit is in that range). Width is now computed with a plain loop, and an audit confirmed no other row-count-scaling call spread or apply() exists in the load path.
- Regression test: parsing 300,001 rows succeeds. End-to-end in the test VM: a 210,000-row pipe-delimited file reads from disk, parses in ~0.4s, loads into SQLite in ~1.8s, and queries correctly.
## 0.1.6 — 2026-11-09
- No more result limits (the ledger's query returned 1,692,797 rows, but only 100,000 could be exported and only the first 10,000 browsed). The 100k maxResultLimit cap is removed: Export now streams the complete result set of the last query to the file, one statement step at a time, with no row cap and without holding the whole result in memory.
- The grid now pages through the entire result set: queries run as a counted subquery, 1,000 rows per page, and Prev/Next fetch further pages from SQLite — all 1,692,797 rows are reachable. A LIMIT you write in your own SQL is still respected, because it bounds the subquery. csvQuery.defaultResultLimit / maxResultLimit are deprecated and no longer restrict anything.
## 0.1.7 — 2026-11-09
- Listing-only release: the 0.1.6 Marketplace listing went live with the stale v0.1.0 README (the .vsix published was the earlier same-named build), which wrongly described a 500-row grid and export capped at 100,000 rows. This version ships the corrected README — 1,000 rows/page paging through the complete result set, streaming export with no row cap, disk reading so the 50 MB sync limit does not apply, deprecated limit settings. No code changes from 0.1.6.
## 0.1.8 — 2026-11-09
- Documentation only (prompted by r/vscode feedback): new README section "Working with numbers" — filter IDs as text, use CAST for numeric comparisons/sorting/totals, plus the two verified gotchas (CAST of empty/non-numeric is 0; strip $ and thousands separators with REPLACE before casting, e.g. $1,234.56 → 1234.56). No code changes from 0.1.7.
## 0.1.9 — 2026-11-10
- Column names: spaces are removed from header names when a file is loaded, so "Spend Category" is queried as SpendCategory and "Revenue Category" as RevenueCategory, with no quoting needed (requested after a real ledger query failed on the spaced name). Original header text is kept as the display label; if two headers collide after stripping (e.g. "Spend Category" and "SpendCategory"), the later one is suffixed _2. Note: saved queries/history that quoted the old spaced names ("Spend Category") need the new name. 32/32 tests, including an end-to-end run of the exact ledger query.
## 0.1.10 — 2026-11-10
- Export is now a proper download flow: the save dialog is pre-filled with "<source>_results.csv" in the source file's own folder (workspace folder or home for untitled sources), so clicking Export Results and confirming saves the CSV right next to the data instead of an un-named file in an arbitrary folder. After the write, the confirmation names the file and offers "Reveal in Finder" / "Open File". Streaming of the complete result set with no row cap is unchanged.
## 1.0.0 — 2026-11-10
- First stable release. CSV Query for VS Code graduates from the 0.1.x series: SQLite SQL on any delimited file (table THIS, all columns TEXT, leading zeros preserved), files read directly from disk with no size-driven sync limit and no result caps (grid pages the complete result set 1,000 rows/page; export streams it in full), space-stripped column names, the export download flow (pre-filled "<source>_results.csv" in the source folder), query history, multi-file joins, and the "Working with numbers" CAST guidance. Battle-tested on a real 1,692,797-row general-ledger export and shaped by user reports from the Marketplace and Reddit. Source now maintained on GitHub.
